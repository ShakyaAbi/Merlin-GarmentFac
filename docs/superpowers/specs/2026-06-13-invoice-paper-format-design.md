# Invoice Paper Format Design

Date: 2026-06-13
Project: Merlin
Scope: Sales invoice and purchase invoice layout, numbering behavior, and VAT calculation

## Goal

Align Merlin sales and purchase invoices with a paper-bill style layout inspired by the provided sample invoice while keeping the existing workflow-oriented screens usable.

The change should make invoice detail and printable invoice output look like a formal business invoice with:

- company header
- invoice number
- party details
- item table
- totals block
- amount in words
- notes
- signature area

## Approved Product Decisions

- Both sales and purchase invoices will use the same paper-style layout structure.
- Labels will be in English.
- VAT must be auto-calculated.
- Sales invoice number will be auto-generated by Merlin but remain editable by the user before final issue.
- Purchase invoice number will always be manually enterable by the user.
- The main difference between the two invoice types is the party section:
  - sales invoice uses customer or buyer details
  - purchase invoice uses supplier details

## Recommended Approach

Update the invoice-focused detail and print surfaces rather than forcing the create or edit forms to fully mimic paper.

This keeps data entry efficient while still giving the user the formal invoice structure where it matters most:

- sales invoice detail and print view
- purchase detail and print view
- invoice summaries and totals behavior that feed those views

Where invoice-create screens already need invoice-number or VAT behavior to support the final output, those fields should be added there without turning the full form into a paper-style document.

## User Experience Design

### 1. Sales Invoice

Sales invoice creation should:

- show a generated invoice number by default
- allow the user to edit that number before issuing the invoice
- auto-calculate VAT from taxable totals
- preserve the current sales workflow around draft, submit, issue, payment, and cancellation

Sales invoice detail should present:

- invoice header in a formal document layout
- buyer details block
- invoice metadata block
- line-item table
- totals block with VAT
- amount in words
- notes and signature footer

### 2. Purchase Invoice

Purchase creation should:

- require manual invoice-number entry
- auto-calculate VAT from taxable totals
- keep supplier and item entry practical for staff use

Purchase detail should present:

- invoice header in the same formal layout as sales
- supplier details block
- invoice metadata block
- raw-material item table
- totals block with VAT
- amount in words
- notes and signature footer

## Shared Invoice Layout

Both invoice types should use this order and structure.

### Header

- Company name
- Invoice title
  - Sales Invoice for sales
  - Purchase Invoice for purchases
- Invoice number

### Party Section

- Buyer or Supplier name
- Address
- PAN or VAT number
- Transaction date

### Metadata Row

Include when data is available:

- payment method
- fiscal year
- issued date

### Items Table

Columns:

- SN
- Item code or HS code
- Description
- Quantity
- Rate
- Amount

Sales rows should represent finished-goods invoice lines.
Purchase rows should represent raw-material purchase lines.

### Totals Block

Rows:

- Subtotal
- Discount
- Taxable Amount
- VAT 13%
- Grand Total

VAT must be computed automatically from the taxable amount.

Base rule:

- taxable amount = max(subtotal - discount, 0)
- VAT = taxable amount * 0.13
- grand total = taxable amount + VAT

If future non-taxable support already exists in the data model, the layout should reserve compatibility for that, but the initial implementation should prioritize the approved 13% VAT flow.

### Footer

- Amount in words
- Notes
- Signature area

## Data and Behavior Changes

### Sales Invoice Numbering

The sales create flow needs a visible invoice-number field with this behavior:

- prefilled by a Merlin-generated value
- editable while the invoice is still in an editable state
- retained in detail and print layouts

The generation mechanism should follow the current repository convention if one already exists. If the current service generates numbers only on issue, the UI should still support editing before issue and the backend should preserve a valid user-edited number.

### Purchase Invoice Numbering

The purchase create flow needs an explicit invoice-number input:

- required for normal purchase creation
- manually entered by the user
- shown in purchase detail and print layouts

### VAT Calculation

Auto-calculation must be deterministic and visible in both invoice types.

Expected behavior:

- recalculate when quantity changes
- recalculate when unit price changes
- recalculate when line discount changes
- update detail and summary immediately on the frontend
- preserve matching totals in backend responses

The frontend must not depend on manual VAT entry for the primary 13% flow.

## Component and Page Impact

Likely frontend touch points:

- `apps/web/pages/sales/SalesInvoiceCreatePage.tsx`
- `apps/web/pages/sales/SalesInvoiceDetailPage.tsx`
- `apps/web/pages/inventory/PurchaseCreate.tsx`
- `apps/web/pages/inventory/PurchaseDetailPage.tsx`
- `apps/web/components/sales/InvoiceItemTable.tsx`
- `apps/web/components/sales/InvoiceTotalsCard.tsx`
- `apps/web/components/inventory/InventoryDocumentShell.tsx`

Expected changes:

- add or expose invoice number fields in create pages
- replace current card-style detail layouts with invoice-document layout sections
- centralize invoice total calculation where practical so sales and purchase behave consistently
- add amount-in-words rendering helper

## Backend Impact

Backend work should be limited to what is needed to support the approved behavior.

Possible touch points:

- sales invoice payload and persistence for editable invoice number
- purchase payload validation for manual invoice number
- total and VAT consistency in API responses

The backend should remain the source of truth for persisted invoice totals and numbers, even if the frontend previews calculations immediately.

## Error Handling

The implementation should handle these cases clearly:

- missing purchase invoice number on create
- duplicate invoice number if uniqueness rules apply
- sales invoice number edited to an invalid value
- negative taxable amount after discount attempts
- invoices with no party PAN or VAT available
- invoices with no notes or signature content

UI guidance:

- validation errors should appear inline near the affected field
- detail pages should still render a clean invoice layout with `-` placeholders where optional data is missing

## Testing Strategy

### Frontend

- sales create page shows editable auto-generated invoice number
- purchase create page requires manual invoice number
- sales VAT recalculates automatically from entered lines
- purchase VAT recalculates automatically from entered lines
- sales detail page renders the new paper-style invoice sections
- purchase detail page renders the new paper-style invoice sections
- totals block shows subtotal, discount, taxable amount, VAT 13%, and grand total

### Backend

- sales invoice accepts stored invoice number when user edits the generated value
- purchase invoice rejects missing invoice number
- VAT and grand total remain consistent with taxable amount

## Out of Scope

- Nepali-language labels
- full replacement of create forms with literal paper replica layout
- advanced tax regimes beyond the approved VAT 13% behavior
- multi-template invoice designer
- PDF engine redesign unless needed to support the same layout structure

## Implementation Notes

The implementation should prefer one reusable invoice-document layout pattern for both sales and purchase rather than building two separate, diverging templates.

That pattern should accept:

- invoice type
- company data
- party data
- metadata
- line items
- totals
- footer details

This keeps future print and export work maintainable and reduces the risk of sales and purchase layouts drifting apart.
